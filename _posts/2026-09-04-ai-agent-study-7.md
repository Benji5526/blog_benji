웹 서비스나 앱을 만들 때 데이터베이스(DB)가 왜 필요한지, 그리고 어떤 역할을 하는지를 배웠다.

## 데이터베이스가 필요한 이유

- **영구적인 보관소:** 화면에 잠깐 뜨는 데이터는 컴퓨터를 끄거나 새로고침하면 사라진다. 만든 서비스의 데이터가 계속 남아있게 하려면 영구적인 창고 역할을 하는 데이터베이스(DB)가 필수적이다.

## 데이터베이스를 이해하는 두 가지 비유

- **도서관:** 데이터베이스는 수만 권의 책(데이터)이 있어도 사서(소프트웨어)를 통해 원하는 책을 금방 찾을 수 있는 도서관과 같다.
- **마법 장난감 상자:** 많은 장난감이 들어 있어도 "파란색 자동차만 꺼내줘"라고 하면 딱 그것만 찾아주는 상자와 같다. 즉, 단순히 쌓아두는 곳이 아니라 원하는 것만 빠르게 찾아주는 곳이다.

## 엑셀이나 메모장과의 차이점

작은 데이터는 엑셀로도 충분하지만, 본격적인 서비스에는 데이터베이스를 써야 하는 세 가지 이유가 있다.

1. **규칙(스키마) 강제:** "이름, 가격, 분류" 등 모양을 미리 정해두어 데이터가 뒤죽박죽 섞이는 것을 막아준다.
2. **압도적인 속도:** 데이터가 수만 건 이상으로 커져도 멈추지 않고 순식간에 원하는 정보를 찾아낸다.
3. **동시성 및 안전성:** 여러 사람이 동시에 접속해도 안전하게 데이터를 사용할 수 있다.

## 오늘의 핵심 결론

데이터베이스는 서비스의 '기억'을 담당한다.

데이터를 넣고 꺼내는 복잡한 코드(SQL)는 AI가 대신 작성해 줄 수 있으니, 학습자는 "내 서비스가 무엇을 기억해야 하는지, 데이터를 어떤 모양으로 저장할지"를 고민하고 설계하는 것이 중요하다.

## 주요 용어 비유 정리

**SQL (에스큐엘 또는 시퀄) - 사서와 대화하는 '전용 언어'**
데이터베이스(도서관)에서 데이터를 꺼내거나 넣을 때 쓰는 명령어. "가격이 1만 원 이상인 파란색 장난감을 찾아줘"라는 명령을 데이터베이스가 알아듣게 텍스트로 적은 규칙 있는 코드다. 예전에는 이 복잡한 문법을 개발자가 다 외워서 써야 했지만, 바이브 코딩을 할 때는 AI에게 "최근 3일 내 가입한 고객 명단 좀 뽑아줘"라고 일상어로 말하면 알아서 SQL 코드로 번역해 준다.

**백엔드 (Backend) - 눈에 보이지 않는 '식당 주방'**
사용자가 화면(프론트엔드)에서 버튼을 누르면, 그 요청을 뒤에서 처리해 주는 시스템. 요리사가 주문을 받고, 냉장고(데이터베이스)에서 재료를 꺼내 요리한 뒤 다시 손님에게 내어주는 모든 뒷단 과정을 말한다.

**스키마 (Schema) - 데이터를 담는 '깐깐한 얼음틀'**
데이터를 저장하기 전에 미리 정해두는 형태와 규칙. 엑셀의 첫 번째 줄(이름, 연락처, 가입일 등)을 아주 빡빡하게 정해두는 것과 같다. "연락처 칸에는 무조건 숫자만 들어가야 해! 글자 쓰면 튕겨낼 거야!"라고 강제해서 데이터가 뒤죽박죽 엉망이 되는 걸 막아준다.

**클라우드 (Cloud) - 인터넷으로 빌려 쓰는 '거대한 디지털 창고'**
예전에는 수만 건의 데이터를 저장하려면 내 방이나 사무실에 비싸고 거대한 컴퓨터(서버)를 직접 사다 놔야 했다. 하지만 지금은 Supabase나 구글, 아마존(AWS) 같은 회사들이 만들어둔 어마어마하게 큰 컴퓨터의 일부를 인터넷을 통해 월세처럼 조금씩 빌려 쓸 수 있다. 인프라 구축 걱정 없이 서비스 기획에만 집중할 수 있게 해주는 고마운 기술이다.

**메모리 vs 영구 저장소(DB)**
- **메모리:** 컴퓨터의 '머릿속 암산'과 같다. 처리 속도는 엄청나게 빠르지만 까먹기 쉽다(새로고침하거나 컴퓨터를 끄면 날아감).
- **영구 저장소(DB):** '다이어리에 적어두기'와 같다. 머리로 암산하는 것보다는 꺼내 보는 데 시간이 아주 미세하게 더 걸릴 수 있지만, 컴퓨터를 껐다 켜도 안전하게 기록이 남아있다.

## 왜 종류가 많을까 - 데이터베이스의 역사

[모두의연구소](https://learn.modulabs.co.kr/camp/147/courses/2190/node-version/5309/steps/26756) 강의에서는 DB의 종류가 왜 이렇게 복잡하고 다양한지, 그 60년의 진화 과정을 배웠다. DB 종류가 많은 이유는 어렵게 만들려는 게 아니라, 각 시대마다 풀어야 할 숙제(병목)가 달랐기 때문이다.

### 역사적 흐름

- **1960년대:** 파일에 무작정 적어두던 방식에서 시작했다.
- **1970년대:** 데이터를 '표'로 깔끔하게 정리하는 혁신(관계형 DB)이 일어났다. 아이디어를 처음 낸 거대 기업 IBM이 망설이는 사이, 래리 엘리슨이 '오라클(Oracle)'이라는 스타트업을 차려 시장을 선점한 비하인드 스토리가 있다.
- **2000년대:** 구글, 아마존처럼 전 세계 엄청난 인원이 동시 접속하는 시대가 오자, 기존의 깐깐한 '표' 방식만으로는 한계가 와서 훨씬 빠르고 유연한 NoSQL이 등장했다.

### 결론

SQL과 NoSQL은 싸우는 경쟁자가 아니라 '용도에 따라 골라 쓰는 도구'다. 다만 처음 서비스를 만들 때는 규칙이 명확한 SQL을 기본으로 시작하는 것이 무난하다.

### 주요 용어 풀이

**관계형 데이터베이스 (Relational Database)**
데이터를 엑셀처럼 반듯한 '표(Table)' 형태로 정리하고, 그 표들을 서로 연결해서(관계) 중복을 없앤 저장 방식. 결제 내역이나 고객 주문 정보처럼 '정확성'이 생명일 때 쓴다.

**SQL (시퀄 / 에스큐엘)**
표 형태의 데이터베이스에게 "어떤 데이터를 찾아줘, 수정해 줘"라고 말하는 전용 명령어. 원래는 영어 문장처럼(SEQUEL) 읽히게 만들려다 상표권 문제로 SQL이 되었기 때문에, 사람마다 '시퀄'이나 '에스큐엘'로 다르게 부르지만 똑같은 뜻이다.

**NoSQL (Not Only SQL)**
이름 때문에 "SQL을 안 쓴다"는 뜻으로 오해받지만, 실제로는 "SQL 말고 다른 것도 쓰자"는 뜻이다. 표의 깐깐한 규칙(스키마)을 버리고 데이터를 문서나 덩어리 형태로 자유롭게 쑤셔 넣을 수 있다. 넷플릭스 영상 추천이나 방대한 소셜 미디어 피드처럼 '엄청난 규모와 빠른 속도'가 필요할 때 쓴다.

**클라우드 데이터베이스 (Cloud Database)**
예전에는 DB를 쓰려면 커다란 컴퓨터를 직접 샀어야 했지만, 이제는 아마존(AWS)이나 구글 등이 거대하게 지어놓은 데이터 창고의 일부를 인터넷으로 빌려 쓰는 방식이다. 관리와 유지를 클라우드 회사가 대신해 주므로 서비스 기획에만 집중할 수 있다.

**폴리글랏 (Polyglot)**
원래는 '여러 언어를 쓰는 사람'이라는 뜻이지만, IT에서는 우버나 넷플릭스 같은 큰 서비스들이 한 가지 DB만 쓰지 않고 돈 계산에는 SQL을, 빠른 로그 저장에는 NoSQL을 섞어서 골라 쓰는 것을 의미한다.

내가 기획하는 서비스의 데이터가 엑셀처럼 깐깐하게 관리되어야 하는 정보(SQL)인지, 아니면 형식 없이 빠르고 방대하게 쌓여야 하는 정보(NoSQL)인지 구분하는 것이 백엔드 설계의 첫걸음이다.

바이브 코딩에는 아주 흔한 실패 패턴이 있다.

> **첫날** — "우와, 하루 만에 화면이 다 만들어졌어!" **다음 주** — "로그인이 자꾸 풀려… 저장한 게 사라져… 클라우드 요금이 왜 이렇게 나왔지?"

화면은 금방 살아나는데 그다음 벽에 부딪힌다. 이유는 하나다. **AI는 "돌아가는 코드"는 잘 만들지만 "안전하고 튼튼한 코드"는 놓친다.** 내가 말하지 않으면 보안을 알아서 챙겨 주지 않는다. 그래서 아래 세 가지는 내가 챙겨야 한다. 문법을 외울 필요는 없고, AI에게 요구할 줄만 알면 된다.

## ① 보안 - 가장 약한 곳

### 얼마나 약한가

보안 회사 Veracode가 AI 모델 100개 넘게 실험했더니 AI가 만든 코드의 약 45%에 보안 구멍이 있었다. 더 놀라운 건, 모델이 똑똑해져도 이 비율이 거의 안 줄었다는 점이다. 문법은 좋아졌지만 안전은 그대로라는 뜻이다.

### 가장 흔한 구멍 - "입력을 그대로 믿는 것"

검색창에 사용자가 이름을 친다. 보통은 "김민준"이라고 치지만, 나쁜 사람은 이름 칸에 명령어처럼 생긴 글자를 넣는다. 서버가 그걸 그대로 믿고 실행하면 데이터가 통째로 털리거나 지워진다. 규칙은 하나다. "사용자가 보낸 값은 일단 의심하고 검사한다."

### 실제로 있었던 일들

| 사고 | 언제 | 무슨 일 |
| --- | --- | --- |
| 에퀴팩스 | 2017 | 알려진 구멍을 방치하다 약 1억 4,300만 명의 주민번호·생일·주소 유출 |
| 소니 PSN | 2011 | 약 7,700만 명 정보 유출, 서비스가 오래 멈춤 |
| 야후 보이스 | 2012 | 비밀번호를 그대로(암호화 없이) 저장했다가 통째로 유출 |
| 마이스페이스 | 2008 | 약 3억 6천만 계정 유출 → 같은 비밀번호 재사용의 위험 |
| MOVEit | 2023 | 파일 전송 프로그램의 허점으로 2,700개 기관·9천만 명 이상 노출 |

공통점이 보인다 — 입력을 함부로 믿었거나, 비밀번호를 그대로 뒀거나, 알려진 구멍을 안 막았거나. 큰 회사도 기본을 놓쳐서 뚫린다.

### AI에게 이렇게 말하기

> "사용자 입력을 검증하고, 비밀번호는 해시로 저장하고, 모든 통신은 HTTPS로 해줘. 흔한 보안 취약점(입력값 주입, XSS)을 막아줘."

이 한 문장이 가장 흔한 구멍들을 막아 준다.

## ② 환경변수 - 비밀은 코드에 적지 않는다

### 흔한 사고 이야기

한 개발자가 급한 마음에 API 키를 코드에 그대로 적어 GitHub에 올렸다. "잠깐인데 뭐 어때." 그런데 몇 분 만에 자동 프로그램(봇)이 그 키를 찾아 훔쳐 갔고, 그 키로 클라우드에서 비싼 작업을 잔뜩 돌려 며칠 뒤 수백만 원짜리 청구서가 날아왔다.

과장이 아니다. 2025년 한 해 공개 GitHub에 유출된 비밀키·비밀번호가 약 2,865만 개(전년 대비 34% 증가)로 역대 최대였고, AI 서비스 키 유출은 1년 새 81% 급증했다.

### 해결책 - 비밀값을 코드 밖에 두기

```
❌ 나쁜 예 (코드에 그대로 박아 넣음)
   apiKey = "sk-a1b2c3d4e5f6..."     ← 올리는 순간 유출

✅ 좋은 예 (코드는 '불러오기'만)
   apiKey = 환경변수에서 불러오기      ← 실제 값은 코드 밖 .env 파일에
   (그리고 .env 는 .gitignore 로 깃에 안 올라가게 막아 둠)
```

한 줄 요약: **코드 = 공개해도 되는 것 / 환경변수 = 절대 공개하면 안 되는 것**

### AI에게 이렇게 말하기

> "API 키와 DB 접속 정보는 코드에 넣지 말고 환경변수로 빼줘. `.env` 파일은 깃에 안 올라가게 해줘."

## ③ 인증 vs 인가 - 콘서트장 비유

로그인 기능에는 사실 두 단계가 숨어 있다.

|  | 콘서트장으로 치면 | 묻는 것 | 실패하면 |
| --- | --- | --- | --- |
| **인증** (Authentication) | 입구의 표 검사원 | "당신, 표 주인 맞아요?" | 401 — "누구세요?" |
| **인가** (Authorization) | VIP 구역의 바운서 | "들어는 왔는데, 이 방에 들어갈 권한은 있어요?" | 403 — "안 돼요" |

로그인에 성공하면 서버가 토큰을 준다. 토큰은 클럽 입구에서 받는 손목 밴드 같은 것이다 — 한 번 확인받고 밴드를 차면, 이후엔 매번 신분증을 안 보여줘도 밴드만 보이면 통과된다.

### 비밀번호는 왜 '해시'로 저장하나

해시는 비밀번호를 되돌릴 수 없는 지문으로 바꾸는 것이다. 달걀을 프라이로 만들 수는 있어도, 프라이를 다시 달걀로 되돌릴 수는 없다. 서버는 원문 대신 지문만 저장하고, 로그인할 때 지문끼리 비교한다. 그래서 데이터가 새어도 비밀번호 원문은 안전하다.

그런데 문제가 하나 있다. 사람들이 흔히 쓰는 비밀번호(`123456`)는 지문도 뻔하다. 그래서 솔트(salt) — 사람마다 다른 무작위 값 — 를 섞어 지문을 낸다. 같은 `123456`이라도 사람마다 지문이 달라진다.

그리고 좋은 서비스는 bcrypt 같은 일부러 느리게 계산되는 방식을 쓴다. 느린 게 장점이다 — 도둑이 수억 개를 대입해 보기 어려워지니까.

### AI에게 이렇게 말하기

> "비밀번호는 솔트를 섞어 bcrypt로 해시해서 저장해줘." 그리고 만든 뒤 되물어야 한다 — "내 데이터를 남이 보면 안 되는데, 권한 확인(인가)이 되어 있나?"

## 곁들여 - 쿠키와 세션 (웹은 원래 건망증이 심하다)

로그인 한 번 하면 페이지를 넘겨도 유지된다. 당연해 보이지만 원래 웹은 기억력이 없다. 초창기 HTTP는 요청 하나하나를 매번 처음 보는 손님처럼 취급했다. 그대로라면 로그인하고 다음 페이지로 가는 순간 로그아웃될 것이다.

이 건망증을 고치려고 나온 것이 쿠키와 세션이다.

|  | 비유 | 하는 일 |
| --- | --- | --- |
| **쿠키** | 내 지갑 속 작은 카드 | 사이트가 번호를 적어 주면 브라우저가 보관했다가 방문할 때마다 보여 줌 |
| **세션** | 사이트 금고 속 내 서류철 | 카드의 번호를 보고 "아, 이 사람!" 하며 내 정보를 꺼냄 |

흐름은 이렇다. ① 로그인 → 서버가 세션을 만들고 고유 번호 발급 → ② 그 번호를 쿠키로 브라우저에 줌 → ③ 이후 요청마다 브라우저가 쿠키를 함께 보냄 → ④ 서버가 번호로 나를 알아봄.

진짜 정보는 브라우저에 두면 안 된다. 쿠키는 사용자가 조작할 수 있어서 `이름=일반사용자`를 `이름=관리자`로 바꾸는 장난이 가능하다. 그래서 브라우저엔 의미 없는 번호만, 진짜 정보는 서버 금고에 둔다. ('로그인 유지' 체크박스는 이 카드를 더 오래 보관하는 것이다.)

## 4강 자가 점검 - 이 습관, 안전할까?

| 습관 | 안전? | 왜 |
| --- | --- | --- |
| API 키를 코드에 적어 GitHub에 올린다 | ❌ | 유출 — 환경변수로 빼야 |
| 사용자가 입력한 값을 그대로 믿고 처리한다 | ❌ | 주입 공격이 들어오는 문 |
| 비밀번호를 솔트 섞어 해시로 저장한다 | ⭕ | 좋다 |
| 모든 사이트에 같은 비밀번호를 쓴다 | ❌ | 한 곳 털리면 다 위험 (마이스페이스의 교훈) |
| 로그인 뒤 '권한(인가)'까지 확인한다 | ⭕ | 인증 + 인가 |

### 오늘의 결론

AI는 아주 빠른 신입 개발자다. 속도는 놀랍지만 보안·비밀 관리·권한 확인은 감독이 필요하다. 신입에게 "결제 로직을 알아서 안전하게 짜 둬"라고 방치하지 않듯이, **입력 검증 · 비밀은 환경변수 · 권한 확인(+비밀번호 해시)** — 이 셋을 프롬프트로 요구하고, 결과를 한 번 더 되묻는 것이 중요하다.

## 배포가 뭔가

배포(deploy)는 내 컴퓨터에만 있던 서비스를 늘 켜진 서버에 올려, 누구나 주소로 들어올 수 있게 하는 것이다.

예전엔 서버 사고 설정하느라 며칠씩 걸리던 전문가의 일이었다. 지금은 비전공자도 클릭 몇 번 + AI의 도움으로 몇 분이면 된다.

## 어디에 올리나 - 셋으로 나눠 올린다 (식당 비유)

| 무엇을 | 어디에 (예) | 식당으로 치면 | 왜 여기에? |
| --- | --- | --- | --- |
| **화면** (프론트) | Vercel · Netlify | 전 세계 여러 지점의 홀 | 손님 가까운 곳에서 빠르게 보여줘야 |
| **서버** (백엔드) | Render · Railway | 늘 켜진 주방 | 요청을 계속 처리해야 |
| **데이터** (DB) | Supabase 등 | 관리형 재료 창고 | 안전하게 보관해야 |

"왜 한 군데에 다 안 올려요?" → 각자 잘하는 게 다르기 때문이다. 화면 전문점은 전 세계에 빠르게 뿌리는 데 강하고, 서버 전문점은 오래 돌아가는 데 강하고, 데이터 전문점은 안전한 보관에 강하다.

무료로 시작한다면 서버는 Render가 무난하다. Railway는 시작 크레딧을 다 쓰면 유료로 넘어간다.

## GitHub에 올리면 자동으로 배포된다

1. 내 코드를 GitHub(코드 저장소)에 올린다
2. 배포 플랫폼(Vercel 등)에서 "이 GitHub 저장소와 연결" 버튼을 누른다
3. 그때부터 플랫폼이 저장소를 지켜보다가, 코드가 바뀔 때마다 자동으로 다시 배포한다
4. 배포가 끝나면 주소를 하나 만들어 준다 (예: `내프로젝트.vercel.app`)

즉 "저장 → 올리기 → 자동 배포"가 한 줄로 이어진다. 한 번 연결해 두면 다음부터는 코드를 고치고 저장하기만 해도 세상에 반영된다.

그리고 이 순간 — 어젯밤 친구에게 보냈지만 안 열리던 그 링크가, 이제 어디서든 열린다.

## 초보가 가장 많이 막히는 세 곳

**① 환경변수 빼먹기** — 내 컴퓨터의 `.env`(비밀값)는 GitHub에 일부러 안 올린다(올리면 유출이니까). 그래서 배포 플랫폼의 설정 화면에 비밀값을 따로 넣어 줘야 한다. → 이걸 빼먹어서 "로컬에선 됐는데 배포하니 안 돼"가 가장 많다.

**② CORS 막힘** — 화면(Vercel)과 서버(Railway)가 서로 다른 주소에 살면, 서버가 "이 화면에서 오는 요청은 허용"이라고 문을 열어 줘야 한다. 안 그러면 브라우저가 "다른 집 요청은 못 받아"라며 막는다. → AI에게 "내 프론트 주소에서 오는 요청을 허용(CORS)해줘"라고 하면 된다.

**③ 무료의 함정** — 대부분 무료 티어가 있지만 트래픽이 늘면 유료로 넘어간다.

## 요금 폭탄 피하기

무료로 시작해도 방심하면 요금이 훅 올라갈 수 있다. 특히 키 유출이나 실수로 만든 무한 반복 때문에. 세 가지만 지키면 된다.

1. **요금 알림을 켜 둔다** — "한 달에 X원 넘으면 알려줘"
2. **한도를 안다** — 내가 쓰는 플랫폼의 무료 한도가 얼마인지 확인
3. **비밀 키를 지킨다** — 유출된 키로 남이 비싼 작업을 돌리면 그 요금은 내 몫

겁주려는 게 아니다. 알고 시작하면 거의 다 예방 가능한 것들이다.

### 무료 티어의 함정 세 가지

**① 잠듦(spin-down)** — 무료 백엔드는 한동안 아무도 안 오면 잠든다. 오랜만의 첫 방문자는 화면이 뜨는 데 1분쯤 걸릴 수 있다. 고장이 아니다. Render 무료가 대표적이다.

**② 기한·일시정지** — 무료 DB가 일정 기간 뒤 사라지거나(Render 무료 Postgres는 30일 후 만료), 안 쓰면 잠시 멈추는(Supabase 7일) 경우가 있다. → 중요한 데이터는 백업을 꼭 따로 받아 두어야 한다.

**③ 요금 폭탄** — 카드가 걸린 서비스는 예산 알림·상한을 걸어 두어야 한다.

"남의 서버를 빌릴 필요 없이, 내 노트북을 24시간 켜두면 그게 서버 아닌가?"라는 질문에서 출발한 강의. 결론부터 말하면 가능하지만, 기본 상태로는 외부에서 절대 접속할 수 없다. 그 이유는 우리 집 인터넷 환경의 구조 때문이다.

## 1. 밖에서 내 컴퓨터로 바로 접속할 수 없는 3가지 이유

- **공유기의 문지기 역할 (NAT):** 우리 집 인터넷은 '공유기'라는 하나의 현관문을 통해 들어온다. 외부 인터넷 세상에서 우리 집을 볼 때는 안방의 노트북인지, 거실의 스마트폰인지 구분하지 못하고 오직 '공유기 한 대'로만 인식한다. 현관문(공유기) 밖에서는 집 안의 특정 방(내 노트북)으로 바로 찾아갈 길이 없다.
- **집 안에서만 쓰는 가짜 주소 (사설 IP):** 공유기는 집 안의 기기들에게 `192.168.0.2` 같은 내부용 번호표를 나누어 준다. 이 번호는 우리 집 안에서만 통하는 내선 번호일 뿐, 밖(인터넷)에서 이 번호를 누른다고 내 컴퓨터로 전화가 걸려 오지 않는다.
- **수시로 이사 가는 집 주소 (유동 IP):** 우리 집의 진짜 바깥 주소(공인 IP)마저도 통신사(KT, SKT 등)가 수시로 바꾼다. 주소가 매번 바뀌니 손님(사용자)이 찾아올 수가 없다.

이러한 구조는 평소에는 해커의 침입을 막아주는 든든한 방패 역할을 하지만, 내 컴퓨터를 세상에 공개하는 '서버'로 만들 때는 큰 장애물이 된다.

## 2. 과거의 복잡하고 위험했던 해결책: 현관문 열어두기

예전에는 이 문제를 해결하기 위해 공유기를 직접 조작하는 다소 위험한 방법을 사용했다. 원리를 이해하기 위해 알아두면 좋은 개념이다.

- **포트 포워딩 (Port Forwarding):** 공유기 설정에 들어가서 "만약 80번 문으로 손님이 찾아오면, 무조건 안방에 있는 내 노트북으로 안내해 줘!"라고 특정 문을 뚫어두는 기술이다.
  - **치명적인 단점:** 집 네트워크에 구멍을 뚫는 셈이라, 전 세계의 해커와 악성 봇(Bot)들이 이 문을 끝없이 두드리며 해킹을 시도한다. 보안상 아주 취약해진다.
  - **더 큰 문제 (CGNAT):** 요즘 통신사들은 주소가 부족해서, 아파트 단지 전체에 큰 공유기를 하나 더 달아버리는 방식(CGNAT)을 쓴다. 이렇게 되면 아무리 내 집 공유기의 문을 열어두어도, 바깥쪽의 더 큰 문이 닫혀 있어서 포트 포워딩 자체가 아예 먹히지 않는 경우가 많다.
- **동적 DNS (DDNS):** 통신사가 우리 집 주소(IP)를 매일 바꾸더라도, `myhome.com` 같은 고정된 이름표를 달아주어 언제든 바뀐 주소를 쫓아갈 수 있게 해주는 서비스다.

## 3. 요즘 시대의 마법 같은 해결책: '터널' 뚫기

포트 포워딩의 위험성과 한계를 극복하기 위해 발상을 완전히 뒤집은 터널링(Tunneling) 기술이 등장했다.

밖에서 문을 열고 들어오길 기다리는 것이 아니라, 내 컴퓨터가 직접 바깥의 안전한 서비스(클라우드)로 먼저 연결 통로(터널)를 뚫어두는 방식이다. 안에서 밖으로 나가는 통로이므로 공유기의 문을 열 필요가 없고, 통신사의 차단(CGNAT)도 무사히 통과한다.

| 서비스 이름 | 초보자를 위한 활용법과 특징 |
| --- | --- |
| **ngrok (엔그록)** | 명령창에 코드 한 줄만 치면 1초 만에 외부 접속 링크를 만들어 준다. "방금 내가 만든 화면, 친구한테 5분만 보여줄게!" 할 때 쓰는 가장 빠르고 간편한 시연용 도구다. |
| **Cloudflare Tunnel** | 무료인데도 접속량 무제한에 튼튼한 보안까지 제공한다. 초기 설정이 조금 복잡하지만, 집에서 24시간 내내 서버를 켜두고 상시 운영할 때 가장 강력하고 안전한 도구다. |
| **Tailscale Funnel** | 모르는 사람에게는 안 보여주고, 내 스마트폰과 내 노트북 등 내 기기들끼리만 안전하게 연결하고 싶을 때 사용하는 사설망 도구다. |

## 4. 라즈베리파이와 나만의 놀이터, 홈랩 (Homelab)

내 노트북을 24시간 켜두면 시끄럽고 전기세가 많이 나오며 수명도 닳는다. 그래서 사람들은 '라즈베리파이(Raspberry Pi)'라는 손바닥만 한 초소형, 초저전력 컴퓨터를 장만한다.

- **홈랩(Homelab)이란?** 집에 이런 작은 컴퓨터나 안 쓰는 구형 PC를 두고 24시간 켜놓으며 나만의 서버를 구축하는 '어른들의 IT 취미 생활'이다.
- **무엇을 할 수 있나?** 나만의 넷플릭스(미디어 서버), 가족 전용 사진첩, 집안 전등을 제어하는 스마트홈 센터 등을 직접 만들 수 있다. 여기에 앞서 말한 '터널'을 연결하면 밖에서도 안전하게 우리 집 서버에 접속할 수 있다.

## 5. 결론: 집 서버 vs 클라우드 배포

내가 만든 Todo 앱이나 웹 서비스를 배포할 때 무엇을 선택해야 할까.

- **집 서버(홈랩)가 어울릴 때:** 인프라가 돌아가는 원리를 깊게 공부하고 싶을 때, 데이터를 남의 회사 서버에 두기 찝찝할 때, 취미로 즐길 때. (가끔 서버가 꺼져도 화낼 사람이 없을 때)
- **클라우드(Vercel, Supabase 등)가 어울릴 때:** 여러분의 첫 배포이자 상용 서비스라면 무조건 클라우드다. 포트폴리오를 제출하거나 실제 사용자에게 24시간 안정적으로 보여줘야 할 때는 무료 클라우드가 보안, 속도, 관리 면에서 압도적으로 유리하고 스트레스가 없다.

## 6. 핵심 전문 용어 완벽 해설

| 용어 | 초보자를 위한 비유와 설명 |
| --- | --- |
| **NAT (네트워크 주소 변환)** | 하나의 외부 주소(아파트 대표 주소)를 집 안의 여러 기기(101동, 102동)가 나눠 쓸 수 있게 교통정리를 해주는 기술이다. 이 때문에 외부에서 특정 기기로 바로 들어갈 수 없다. |
| **사설 IP (Private IP)** | 공유기가 나누어주는 `192.168.x.x` 형태의 가짜 주소다. 인터넷 세상에서는 검색되지 않는 내부용 내선 번호다. |
| **유동 IP (Dynamic IP)** | 통신사가 IP 주소를 절약하기 위해, 접속할 때마다 또는 주기적으로 계속 바꿔서 빌려주는 외부 주소다. |
| **포트 포워딩 (Port Forwarding)** | 외부에서 특정 번호표(포트)를 달고 찾아오면, 공유기가 확인하고 집 안의 특정 컴퓨터로 바로 직행할 수 있게 길을 열어두는 위험한 기능이다. |
| **DDNS (동적 DNS)** | 주소가 자꾸 이사 가는(유동 IP) 우리 집 서버에, 절대 바뀌지 않는 고정된 간판(도메인 주소)을 달아주는 서비스다. |
| **CGNAT (Carrier-grade NAT)** | 통신사(SK, KT 등)가 사용자에게 아예 진짜 외부 주소조차 주지 않고, 통신사 안에서 거대한 공유기를 한 번 더 거치게 만드는 깐깐한 시스템이다. 이것 때문에 포트 포워딩이 막히는 경우가 많다. |
| **터널 (Tunnel / Tunneling)** | 포트 포워딩의 한계(보안, CGNAT)를 뚫기 위해, 내 컴퓨터에서 먼저 바깥 세상(클라우드)으로 암호화된 비밀 통로를 파고 나가서 손님을 모셔오는 현대적인 접속 기술이다. |

## 1. 프론트엔드와 백엔드의 만남: '연결'의 진정한 의미

지금까지 만든 예쁜 화면(프론트엔드)과 안 보이는 곳에서 데이터를 처리할 서버(백엔드)를 하나로 묶어주는 '연결(Integration)' 단계다. 식당으로 비유하자면, 멋지게 꾸며놓은 홀(화면)과 요리를 만드는 주방(서버) 사이에 드디어 '웨이터(API)'를 고용하여 주문을 주고받기 시작하는 결정적인 순간이다.

초보자들이 코딩을 포기하는 가장 큰 고비가 바로 이 지점이다. 두 개의 다른 시스템이 소통해야 하므로 에러가 잦기 때문이다. 하지만 안전한 규칙과 순서를 따른다면, 복잡한 연결 과정도 매끄럽게 통과할 수 있다.

## 2. 절대 실패하지 않는 3단계 연결 순서

AI에게 "내 앱 전체를 프론트부터 백엔드까지 한 번에 다 만들어줘!"라고 명령하는 것은 초보자가 가장 많이 하는 실수다. AI는 기억력(컨텍스트 한계)과 집중력에 제한이 있어서 너무 큰 작업을 주면 중간에 코드를 빼먹거나 엉뚱하게 짜버린다. 따라서 다음 3단계로 작게 쪼개어 작업해야 한다.

- **1단계: 목업(가짜) 화면 먼저 만들기** — 진짜 서버가 없어도 화면이 잘 동작하는지 확인하기 위해, 임시 가짜 데이터(목업)를 넣어 프론트엔드 화면만 완벽하게 먼저 완성한다.
- **2단계: 백엔드 API 창구(엔드포인트) 열기** — 화면은 놔두고, 이제 서버 쪽 코드를 짠다. 화면에서 요청을 보낼 때 응답을 받아줄 구체적인 주소(예: `/api/users`)와 기능을 만든다.
- **3단계: 가짜 데이터를 진짜 데이터로 교체하기** — 다시 화면 코드로 돌아와서, 1단계에서 썼던 가짜 데이터를 지우고 2단계에서 만든 서버 주소로 직접 데이터를 요청하도록 연결 선을 이어준다.

## 3. 초보자가 겪는 3대 지옥과 탈출(처방) 가이드

프론트와 백엔드를 연결할 때 무조건 마주치게 되는 3가지 흔한 에러와 그 해결책이다.

1. **계약 불일치 (데이터 모양이 다름)**
   - **증상:** 화면에는 사용자 '이름'과 '나이'가 필요한데, 서버는 '닉네임'과 '생년월일'을 보내줄 때 발생한다. 화면에 데이터가 뜨지 않고 `undefined`라는 에러가 나타난다. AI에게 양쪽 코드를 따로 짜게 놔두면 발생한다.
   - **처방:** 코딩을 시작하기 전에 'API 명세(설계도)'를 문서로 먼저 작성해야 한다. 양쪽 모두 이 설계도를 기준으로만 코드를 짜도록 AI를 통제해야 한다.
2. **로딩과 에러 상태 누락 (화면이 멈춘 것 같음)**
   - **증상:** 사용자가 버튼을 눌렀는데 서버에서 응답이 올 때까지 화면이 멈춰있거나 깜빡거린다.
   - **처방:** 데이터를 부를 때는 반드시 3가지 상태(로딩 중 / 성공 시 / 실패 시)를 모두 준비해야 한다. AI에게 "데이터를 불러오는 동안 보일 로딩 스피너와, 서버 에러가 났을 때 보여줄 에러 메시지 화면도 같이 짜줘"라고 명확히 요구해야 한다.
3. **CORS 및 주소 연결 오류**
   - **증상:** 내 컴퓨터(로컬)에서는 잘 되던 앱이, 인터넷에 배포(공개)하는 순간 서로 통신이 막혀버린다.
   - **처방:** 백엔드 문지기에게 프론트엔드의 주소를 "이 주소는 안전한 우리 편이니 통과시켜 줘"라고 등록(CORS 설정)해야 하며, 접속 주소는 코드에 직접 적지 않고 '환경변수'라는 비밀 상자에 숨겨서 연결해야 한다.

## 4. AI를 똑똑하게 부리는 '바이브 코딩' 프롬프트 팁

- **API 명세서를 법전처럼 다루기:**

  > "우리가 만들 기능의 엔드포인트(주소) 목록과, 주고받을 데이터의 JSON 모양 예시를 먼저 명세 문서로 정리해 줘. 앞으로 프론트와 백엔드 코드를 짤 때는 무조건 이 문서를 기준으로만 작업하자."

- **수직 슬라이스 (한 놈만 팬다):** 회원가입, 로그인, 게시글 작성을 동시에 만들지 않는다. "오늘은 회원가입 기능 딱 하나만 화면부터 DB 저장까지 뚫어보자"라는 식으로 하나의 기능(수직)을 끝까지 완성하고 테스트한 뒤 다음으로 넘어간다.
- **체크포인트(커밋) 만들기:** AI는 가끔 멀쩡히 잘 돌아가던 코드도 실수로 망가뜨린다. 한 단계가 성공적으로 끝날 때마다 반드시 현재 상태를 저장(Git Commit)하여 언제든 과거로 돌아갈 수 있는 안전망을 만들어야 한다.

## 5. 배포 전 필수! 보안 점검 체크리스트

AI는 "안전한 코드"보다 "일단 겉보기에 돌아가는 코드"를 짜는 데 집중한다. 따라서 내가 직접 보안 감독관이 되어 AI의 코드를 검사해야 한다.

- **이중 검증 (백엔드를 깐깐하게):** 프론트엔드 화면에서 "비밀번호는 8자리 이상 입력하세요"라고 막아두었더라도, 해커는 화면을 무시하고 서버를 직접 공격할 수 있다. 서버(백엔드) 코드에서도 반드시 비밀번호가 8자리가 맞는지 한 번 더 검사(검증)해야 한다.
- **하드코딩(비밀번호 노출) 금지:** API 비밀키나 데이터베이스 주소를 코드 파일에 그대로 적으면(하드코딩), 인터넷에 코드가 공개될 때 전 세계 해커들에게 비밀번호를 광고하는 꼴이 된다. 특히 프론트엔드 코드에 `NEXT_PUBLIC_`이나 `VITE_`라는 글자가 붙은 변수는 누구나 브라우저에서 훔쳐볼 수 있으므로, 진짜 민감한 비밀번호에는 절대 저 글자를 붙이면 안 된다.

가장 쉬운 보안 점검 프롬프트:

> "이 코드 전체를 꼼꼼히 점검해 줘. 1) 하드코딩된 비밀값이 있는지, 2) 백엔드에서 입력값 검증을 빼먹지 않았는지, 3) CORS 설정은 안전한지 보안 전문가의 관점에서 찾아내고 수정해 줘."

## 6. 핵심 전문용어 완벽 해설

| 용어 | 초보자를 위한 쉬운 설명 및 비유 |
| --- | --- |
| **API 명세** (API Contract / Specification) | 식당의 '메뉴판 및 주문서 양식'이다. 프론트엔드(손님)가 백엔드(주방)에 무엇을 어떻게 요청하면, 어떤 모양의 데이터(요리)가 나올지 미리 꼼꼼하게 약속해 둔 문서다. |
| **엔드포인트** (Endpoint) | 백엔드 서버에 뚫려 있는 구체적인 '접수 창구 주소'다. (예: `/api/login`은 로그인 전용 창구, `/api/posts`는 게시글 전용 창구) |
| **JSON** (제이슨) | 프론트엔드와 백엔드가 데이터를 주고받을 때 사용하는 '만국 공용어(택배 상자)'다. `{"이름": "김모두", "나이": 20}` 처럼 이름표와 실제 값을 세트로 묶어 데이터를 깔끔하게 전달하는 규칙이다. |
| **수직 슬라이스** (Vertical Slice) | 케이크를 빵 따로, 크림 따로 만드는 것이 아니라, 위에서 아래까지 한 조각을 푹 떠서 완벽한 한 입을 만드는 개발 방식이다. 화면(UI) → 서버(API) → 저장(DB)까지 딱 하나의 기능만 먼저 완벽하게 연결해 보는 것을 뜻한다. |
| **하드코딩** (Hardcoding) | 아이디, 비밀번호, 서버 주소 같은 중요한 정보를 코드 파일 안에 수정할 수 없는 글씨로 쾅쾅 박아 넣는 행위다. 보안에 매우 취약하며 반드시 '환경변수'로 빼내어 숨겨야 한다. |
| **CORS** (교차 출처 리소스 공유) | 웹 브라우저가 가진 기본적인 방패다. 내 프론트엔드 주소(`A.com`)와 내 백엔드 주소(`B.com`)가 서로 다를 때, "모르는 주소에서 온 데이터는 위험해!"라며 통신을 콱 차단해 버리는 현상이다. 백엔드에서 프론트 주소를 허용 리스트에 적어주어야 해결된다. |
| **풀스택** (Full-Stack) | 눈에 보이는 프론트엔드(화면)와 눈에 보이지 않는 백엔드(서버+데이터베이스) 기술을 모두 다루어, 혼자서 온전한 웹 서비스를 처음부터 끝까지 만들어내는 것을 의미한다. |
