## 화면 뒤에 서버가 필요한 이유

[모두의연구소](https://learn.modulabs.co.kr/camp/147/courses/2190/node-version/5310/steps/26766) 강의에서 우리가 만든 화면(프론트엔드)이 왜 세상에 공개되지 않는지, 컴퓨터를 껐다 켜면 데이터가 왜 사라지는지 그 원인을 짚어보고 백엔드(서버)의 필요성을 배웠다.

### 1. 주요 문제와 원인

- **친구에게 주소를 줬는데 안 열리는 이유 (`localhost:3000`)**
  `localhost`는 '내 컴퓨터'를 뜻하는 주소다. 친구가 자기 컴퓨터에서 이 주소를 입력하면 내 화면이 아니라 친구 자신의 컴퓨터를 찾기 때문에 연결할 수 없다.

- **새로고침하거나 노트북을 껐다 켜면 입력한 내용이 사라지는 이유**
  내 컴퓨터 안에서만 임시로 실행되고 있어, 데이터를 저장해 둘 곳(서버/데이터베이스)이 없기 때문이다.

### 2. 프론트엔드와 백엔드의 역할 비교 (식당 비유)

- **프론트엔드 (화면):** 손님 눈에 보이는 '홀' (메뉴판, 자리, 인테리어 등)
- **백엔드 (서버):** 눈에 안 보이는 '주방 겸 창고' (데이터 저장, 회원 확인, 계산 처리 등)

버튼 색상 변경이나 애니메이션처럼 "내 화면 안에서 잠깐 보이고 마는 것"은 서버 없이도 가능하지만, 여러 사람이 나눠 쓰거나 껐다 켜도 데이터가 남아야 하는 서비스는 백엔드가 필수적이다.

### 3. 인터넷과 서버의 발전 과정

- **1969년 (ARPANET):** 멀리 있는 컴퓨터끼리 메시지를 주고받는 인터넷의 씨앗이 시작됐다.
- **1970~80년대 (TCP/IP):** 서로 다른 컴퓨터가 대화할 수 있는 공통 규칙(IP 주소 등)이 자리 잡았다.
- **1989~1991년 (웹과 HTTP):** 문서와 링크를 잇는 월드 와이드 웹과 HTTP 규칙, 웹 주소(URL)가 탄생했다.
- **2000년대 이후 (클라우드):** 직접 서버 컴퓨터를 사지 않고 아마존이나 구글 등의 서버를 빌려 몇 분 만에 서비스를 올릴 수 있게 됐다.

### 4. 대규모 접속을 버티는 방법

- **수평 확장 (로드 밸런서):** 똑같은 서버를 여러 대 두고 안내 직원을 통해 손님을 분산시킨다.
- **캐시 및 CDN:** 자주 찾는 인기 이미지나 파일을 손님과 가까운 여러 지점에 미리 복사해 두어 빠르게 열리도록 한다.

## 식당 비유로 보는 프론트엔드와 백엔드의 역할 분리

식당 하나만 알면 서버도 프론트엔드도 이해할 수 있다. 손님이 앉는 홀, 요리하는 주방, 재료가 쌓인 창고 — 이 셋의 관계가 곧 웹 서비스의 구조다.

- **홀 (메뉴판, 주문하기):** 프론트엔드. 손님(사용자)의 휴대폰이나 컴퓨터에서 돌아간다.
- **주방:** 백엔드. 손님은 절대 들어올 수 없고, 24시간 불이 켜져 있는 건물(서버) 안에 있다.
- **창고:** 데이터베이스. 회원 정보와 주문 기록이 쌓인다. 주방(백엔드)이 창고(DB)에서 재료를 꺼내 쓰듯, 데이터를 읽고 쓴다.

홀은 손님의 기기에 있고, 주방과 창고는 서버 안에 있다. 이 경계가 곧 보안의 경계다.

### 주문 하나가 지나가는 길

1. 손님이 메뉴판을 보고 **주문하기**를 누른다. — 프론트엔드가 화면을 그려 보여준 결과
2. 홀에서 주문서를 적어 주방으로 넘긴다. — 프론트엔드가 서버에 요청을 보낸다
3. 주방이 주문서를 확인한다. 재고가 있나, 결제가 됐나. — 백엔드의 판단
4. 필요한 재료를 창고에서 꺼내고, 주문 기록을 창고에 남긴다. — 데이터베이스 읽기와 쓰기
5. 완성된 요리를 홀로 내보낸다. — 서버의 응답
6. 홀이 요리를 손님 앞에 예쁘게 놓는다. — 프론트엔드가 받은 데이터로 화면을 바꾼다

### 누가 무엇을 맡는가

| 프론트엔드가 하는 일 | 백엔드가 하는 일 |
| --- | --- |
| 입력창과 버튼을 화면에 그린다 | 받은 비밀번호가 맞는지 대조한다 |
| 빈칸으로 눌렀을 때 경고를 띄운다 | 맞으면 출입증(로그인 상태)을 발급한다 |
| 입력값을 모아 서버로 보낸다 | 이 사람이 볼 수 있는 데이터만 골라 보낸다 |
| 결과에 따라 화면을 바꾼다 | 로그인 시도 기록을 남긴다 |

비밀번호 대조를 프론트엔드에서 하면 안 되는 이유는 하나다. 프론트엔드 코드는 손님의 기기에서 돌아가므로 누구나 열어볼 수 있다. 주방 문을 열어두는 것과 같다.

## 네트워크 기본기 - 주소가 화면이 되기까지

[모두의연구소](https://learn.modulabs.co.kr/camp/147/courses/2190/node-version/5310/steps/26768) 강의에서는 주소를 입력하고 엔터를 누른 뒤 화면이 뜨기까지 벌어지는 과정을 배웠다.

### 1. 웹 접속을 완성하는 4가지 기본 요소

**① 도메인과 DNS (이름을 주소로)**
- **도메인:** 사람이 외우기 쉬운 문자 주소(`mysite.com`).
- **DNS:** 도메인을 실제 컴퓨터 번호인 **IP 주소**로 바꿔주는 전화번호부 역할.
- **추상화의 이점:** 도메인이라는 이름을 중간에 두면, 실제 서버나 IP가 바뀌어도 사용자 주소를 바꿀 필요 없이 DNS 설정 한 줄만 고치면 된다.

**② 서버와 호스팅 & 내부망/외부망 (주소의 목적지)**
- **서버:** 24시간 켜져 있는 컴퓨터. 최근에는 직접 서버를 사지 않고 AWS/구글 등의 클라우드를 빌려 사용한다.
- **내부망(LAN):** 공유기 안쪽의 '우리끼리' 공간(`192.168.x.x` 또는 `localhost`).
- **외부망(WAN):** 전 세계 인터넷 공간. 서비스를 공개한다는 것은 내부망의 자원을 외부망에서 접근 가능하도록 만드는 것이다.

**③ 포트와 방화벽 (접근 문과 경비)**
- **포트:** 컴퓨터 안의 세부 창구 번호(예: 웹 기본 포트 `80`, `443`, 개발용 `3000`). IP가 건물 주소라면 포트는 호실 번호다.
- **방화벽:** 포트의 출입을 통제하는 경비 역할.

**④ HTTP / HTTPS (통신 언어 및 보안)**
- **HTTP:** 브라우저와 서버 간의 요청(`GET`)과 응답(`200 OK`) 규칙.
- **HTTPS:** 대화 내용을 암호화하여 주고받는 안전한 버전. 공개키/개인키 방식을 활용하며, SSL/TLS 인증서를 통해 서버의 신원과 보안을 보증한다.

### 2. 데이터 이동 방식과 동작 원리

- **패킷(Packet) 단위 이동:** 데이터는 통째로 이동하지 않고 작은 '패킷' 단위로 쪼개져 서로 다른 경로를 거쳐 전달된 뒤 도착지에서 다시 조립된다.
- **주소 입력 후 1초 동안 벌어지는 일:**
  1. DNS에 도메인 IP 조회
  2. 서버 IP의 특정 포트(HTTPS 443번 등)로 연결
  3. HTTP 요청 전달 및 서버 응답 수신
  4. 브라우저가 화면 랜더링

### 3. 주요 HTTP 상태 코드 요약

서버의 처리 결과를 나타내는 3자리 숫자 응답 코드다.

| 구분 | 의미 | 대표 코드 예시 |
| --- | --- | --- |
| **2xx** | **성공** | `200 OK` (정상 처리) |
| **3xx** | **리다이렉션** | `301 / 302` (페이지 이동) |
| **4xx** | **클라이언트(요청자) 오류** | `401` (로그인 필요), `403` (권한 없음), `404` (페이지 없음) |
| **5xx** | **서버 오류** | `500` (서버 내부 에러) |

## 주문서는 어떻게 부산까지 갔을까 - 웹 동작 원리

홀과 주방이 멀리 떨어져 있다면, 주문서를 실어 나를 우편 시스템이 필요하다. 인터넷이 하는 일이 정확히 그것이다.

- **첫째, 주소를 알아낸다:** 내 컴퓨터가 "naver.com 어디예요?"라고 물으면 DNS가 "223.130.200.107요"라고 답한다. DNS는 인터넷 주소록이다.
- **둘째, 짐을 나눠 부친다:** 데이터는 잘게 쪼개져 번호를 달고 간다(패킷). IP는 건물 주소, 포트는 호수다(예: `443호`). 편지들은 서로 다른 길로 갈 수도, 순서가 뒤바뀌어 도착할 수도 있지만 받는 쪽이 번호대로 다시 맞춘다. 길 하나가 막혀도 우회할 수 있게 하려고 데이터를 쪼개 보내는 것이며, 이 덕분에 인터넷이 잘 끊기지 않는다.

### 배달 방식에도 두 종류가 있다

| TCP — 등기우편 | UDP — 그냥 던지기 |
| --- | --- |
| 도착 확인을 받는다 | 확인하지 않는다 |
| 빠진 편지는 다시 보낸다 | 잃어버려도 넘어간다 |
| 느리지만 하나도 안 빠진다 | 빠르지만 조금 새어나간다 |
| 웹, 이메일, 파일 전송 | 영상 통화, 실시간 게임 |

영상 통화가 가끔 뭉개져도 계속 흘러가는 건 UDP를 쓰기 때문이다. 끊긴 0.1초를 다시 받아봐야 이미 늦었으니, 차라리 버리고 다음 장면으로 간다.

### 브라우저는 받은 문서로 화면을 조립한다

서버가 보내주는 건 완성된 그림이 아니라 설명서에 가깝다. 브라우저가 그걸 읽어가며 눈앞의 화면을 만들어낸다.

- **HTML:** 뼈대 — 무엇이 있는가
- **CSS:** 옷 — 어떻게 보이는가
- **JavaScript:** 움직임 — 누르면 무엇이 일어나는가

셋 다 프론트엔드다. 화면을 만드는 재료가 역할별로 셋으로 나뉘어 있을 뿐이다.

### 엔터를 누른 뒤 벌어지는 일

1. 브라우저가 DNS에 주소를 묻는다 — 이름을 숫자로 바꾼다
2. 알아낸 IP의 443호로 연결을 연다 — TCP로 등기 배달 창구를 튼다
3. 서로 열쇠를 교환해 봉투를 봉인한다 — HTTPS, 주소창의 자물쇠
4. "이 페이지 주세요"라고 요청을 보낸다 — HTTP 요청
5. 서버가 HTML 문서를 돌려보낸다 — 백엔드가 창고에서 데이터를 꺼내 만든 결과
6. 브라우저가 읽으며 화면을 조립한다 — 필요한 이미지와 파일을 또 요청한다

6번이 끝이 아니다. 페이지 하나를 띄우는 데 이 왕복이 수십 번 일어난다. 그 전부가 대개 1초 안에 끝난다.

## 주문서와 요리 - 요청, 응답, 그리고 주방의 규칙

앞서 홀(프론트엔드)과 주방(백엔드)을 나누고 그 사이를 오가는 우편 시스템(네트워크)을 봤다. 이번엔 그 사이를 오가는 주문서 한 장과, 주방이 그걸 받아 무슨 판단을 하는지를 확대해서 본다.

### 1. 요청 - 형식이 정해진 주문서

식당의 주문서에는 빈칸이 정해져 있다. 아무렇게나 쓴 쪽지를 던지면 주방이 못 알아듣는다. HTTP 요청도 마찬가지로 네 칸으로 되어 있다.

```
POST  /orders  HTTP/1.1              ← ① 어떻게  ② 무엇에 대해
Host: cafe.example.com               ← ③ 여백의 메모 (헤더)
Authorization: Bearer eyJhbGciOi...
Content-Type: application/json
{                                    ← ④ 실제 내용 (바디)
  "menu": "아메리카노",
  "size": "L",
  "iced": true
}
```

**① 메서드 - 무엇을 해달라는 건가**

주문서의 종류다. 네 가지만 알면 대부분 커버된다.

| 메서드 | 식당에서 | 뜻 | 데이터가 바뀌나 |
| --- | --- | --- | --- |
| `GET` | "메뉴판 좀 보여주세요" | 조회 | 안 바뀜 |
| `POST` | "이거 하나 주세요" | 새로 만들기 | 바뀜 |
| `PUT` / `PATCH` | "샷 하나 추가로 바꿔주세요" | 수정 | 바뀜 |
| `DELETE` | "주문 취소할게요" | 삭제 | 바뀜 |

`GET`만 데이터를 바꾸지 않는다는 점이 중요하다. 그래서 브라우저는 `GET` 결과를 마음대로 저장해두거나 미리 불러올 수 있다. 반대로 `GET`으로 데이터를 바꾸도록 만들면 사고가 난다. "목록 보기"를 눌렀을 뿐인데 주문이 취소되는 상황이 벌어지니까.

**② 경로 - 무엇에 대한 이야기인가**

`/orders`, `/users/42`, `/products/17/reviews` 처럼 대상을 가리킨다. 경로에는 명사를 쓰고 동작은 메서드로 표현하는 것이 관례다.

- 좋음: `POST /orders`
- 나쁨: `POST /createOrder` (동작이 두 군데에 중복)

**③ 헤더 - 주문서 여백의 메모**

내용물은 아니지만 처리에 필요한 정보들이다.

- `Authorization` — 출입증. "나 로그인한 그 사람이에요"
- `Content-Type` — "내용물은 JSON 형식입니다"
- `Accept` — "답장은 JSON으로 주세요"
- `User-Agent` — "저는 아이폰 사파리에서 왔어요"

**④ 바디 - 실제 내용물**

무엇을 만들거나 바꿔달라는지의 알맹이다. `GET`과 `DELETE`에는 보통 없다. 조회와 삭제는 대상만 지목하면 되니까.

### 2. 응답 - 주방의 답변

```
HTTP/1.1 201 Created                 ← 상태 코드
Content-Type: application/json
{
  "orderId": 8127,
  "waitMinutes": 4,
  "pointsEarned": 45
}
```

**상태 코드 - 맨 앞자리가 전부다**

세 자리 숫자지만, 실은 첫 자리만 봐도 상황을 알 수 있다.

| 대역 | 뜻 | 식당에서 |
| --- | --- | --- |
| `2xx` | 성공 | "네, 나왔습니다" |
| `3xx` | 다른 곳으로 | "그 메뉴는 2호점에서 팝니다" |
| `4xx` | 손님 잘못 | "그런 메뉴 없는데요" |
| `5xx` | 주방 잘못 | "죄송합니다, 가스가 나갔어요" |

`4xx`와 `5xx`의 구분이 실무에서 가장 중요하다. `4xx`는 손님이 요청을 고쳐서 다시 보내면 되고, `5xx`는 손님이 뭘 해도 소용없고 개발자가 고쳐야 한다.

자주 만나는 것들:

| 코드 | 이름 | 언제 |
| --- | --- | --- |
| `200` | OK | 조회 성공 |
| `201` | Created | 새로 만들어짐 (주문 접수됨) |
| `400` | Bad Request | 주문서 양식이 틀림 |
| `401` | Unauthorized | 출입증이 없음 — 너 누구야? |
| `403` | Forbidden | 출입증은 있는데 권한이 없음 — 너인 건 알겠는데 안 돼 |
| `404` | Not Found | 그런 건 없음 |
| `409` | Conflict | 이미 있음 (중복 가입 등) |
| `500` | Internal Server Error | 주방이 터짐 |

`401`과 `403`은 초보자가 가장 많이 헷갈린다. 401은 신원 확인 실패, 403은 자격 부족이다. 로그인을 안 했으면 401, 로그인은 했는데 남의 주문서를 열려고 하면 403이다.

### 3. 비즈니스 로직 - 주방의 규칙

여기가 핵심이다.

**정의:** 비즈니스 로직은 그 서비스만의 규칙과 판단이다.

- 커피를 시키면 포인트를 5% 쌓아준다
- 재고가 0이면 주문을 받지 않는다
- 5만 원 이상이면 배송비를 면제한다
- 미성년자에게는 술을 팔지 않는다
- 주문 후 5분이 지나면 취소할 수 없다

이런 것들은 프로그래밍 기술이 아니라 그 가게의 정책이다. 사장이 바뀌면 바뀌고, 법이 바뀌면 바뀐다.

**기술 코드와 비즈니스 로직의 차이**

| 기술 코드 | 비즈니스 로직 |
| --- | --- |
| JSON을 파싱한다 | 재고가 있는지 확인한다 |
| 데이터베이스에 연결한다 | 5만 원 넘으면 배송비를 뺀다 |
| 비밀번호를 암호화한다 | 3번 틀리면 계정을 잠근다 |
| 어느 서비스에나 똑같다 | 이 서비스에만 있다 |

기술 코드는 남이 만든 걸 가져다 쓸 수 있다. 비즈니스 로직은 아무도 대신 써줄 수 없다. 그래서 이게 진짜 자산이다.

**주문 하나가 주방에서 거치는 판단**

`POST /orders` 요청이 들어왔을 때 실제로 벌어지는 일이다.

```
주문서 도착
   │
   ├─ 1. 양식 검사   "메뉴 이름이 비었네?"        → 실패 시 400
   │
   ├─ 2. 신원 확인   "출입증이 유효한가?"          → 실패 시 401
   │
   ├─ 3. 권한 확인   "이 사람이 주문할 수 있나?"    → 실패 시 403
   │
   ├─ 4. 규칙 판단   "재고 있나? 영업시간인가?
   │                 포인트는 얼마 쌓지?"          → 실패 시 409 등
   │
   ├─ 5. 데이터 변경  재고 -1, 주문 기록 생성,
   │                 포인트 +45  ← 전부 성공하거나 전부 취소 (트랜잭션)
   │
   └─ 6. 응답 만들기  201 Created + 주문 번호
```

1~3번은 문지기 역할이라 어느 서비스에나 비슷하게 있다. 4번과 5번이 비즈니스 로직이다. 이 가게가 무엇을 파는 가게인지가 여기 담긴다.

**5번에서 트랜잭션이 왜 필요한가**

재고를 1 줄였는데 주문 기록 저장에 실패했다고 해보자. 재고는 사라졌는데 주문은 없는 상태가 된다. 커피 한 잔이 증발한다. 그래서 4~5번의 변경들을 하나의 묶음으로 처리한다. 전부 성공하거나, 하나라도 실패하면 전부 없던 일이 된다. 이것이 트랜잭션이다.

### 4. 주방도 안에서 역할이 나뉜다

주방이 커지면 요리사 한 명이 다 하지 않는다. 백엔드 코드도 보통 세 층으로 나눈다.

```
   요청                                                    응답
    │                                                       ▲
    ▼                                                       │
┌─────────────┐    ┌─────────────┐    ┌──────────────┐   ┌──────────┐
│ Controller  │───▶│   Service   │───▶│  Repository  │──▶│    DB    │
│  홀 직원     │    │   요리사     │    │  창고 담당    │   │   창고    │
└─────────────┘    └─────────────┘    └──────────────┘   └──────────┘
 주문서를 받아       재고 확인,           재료를 꺼내고         데이터가
 양식을 확인하고     포인트 계산,          넣는 일만            실제로
 넘긴다             규칙 판단            담당                 쌓이는 곳
 "형식이 맞나?"     "이 주문이 말이       "SQL은 내가
                    되나?"                쓸게"
                    ↑
              비즈니스 로직은
                여기 모인다
```

이렇게 나누는 이유는 하나다. 규칙이 바뀔 때 한 군데만 고치기 위해서다. 포인트 적립률을 5%에서 7%로 바꾼다고 할 때, 그 숫자가 코드 여기저기에 흩어져 있으면 하나를 빠뜨린다. Service 층 한 곳에만 있으면 한 줄만 고치면 된다.

### 5. 왜 이 판단을 프론트엔드에서 하면 안 되는가

앞서 "프론트엔드 코드는 손님 기기에서 돌아가니 누구나 열어볼 수 있다"고 했다. 비즈니스 로직에서 이 문제가 가장 크게 터진다.

**나쁜 예:** 프론트엔드가 가격을 계산해서 서버에 보낸다

```
프론트: "아메리카노 L사이즈, 결제 금액 4500원입니다"
서버:   "네, 4500원 결제합니다"
```

손님이 코드를 열어 `4500`을 `100`으로 바꾸면 커피를 100원에 산다.

**좋은 예:** 프론트엔드는 무엇을 원하는지만 말하고, 계산은 서버가 한다

```
프론트: "아메리카노 L사이즈 주세요"
서버:   (내가 가진 가격표로 직접 계산) "4500원입니다. 결제합니다"
```

**원칙:** 프론트엔드가 보낸 값은 전부 거짓말일 수 있다고 가정한다.

프론트엔드에도 검사를 넣긴 한다. 하지만 그건 친절이지 보안이 아니다. 빈칸으로 눌렀을 때 서버까지 안 갔다 오고 바로 알려주니 손님이 편할 뿐이다. 진짜 검사는 반드시 서버에서 한 번 더 한다. 검사가 두 군데에 있는 건 낭비가 아니라 정상이다.

### 6. 자주 헷갈리는 것들

**"응답이 왔으면 성공한 거 아닌가요?"**
아니다. `404`도 `500`도 멀쩡히 도착한 응답이다. 편지가 도착한 것과 좋은 소식인 것은 다르다.

**"API가 뭔가요?"**
지금까지 설명한 이 주문 창구 전체가 API다. "어떤 주문서를 어떤 양식으로 보내면 무엇을 돌려준다"는 약속의 목록이다. 메뉴판이 손님과 주방 사이의 약속인 것과 같다.

**"JSON이 뭔가요?"**
데이터를 주고받을 때 쓰는 표기법이다. 사람도 읽을 수 있고 기계도 읽을 수 있게 만든 형식이라 요즘 API는 거의 다 이걸 쓴다. 위 예시의 중괄호 덩어리가 JSON이다.

**"비즈니스 로직이 꼭 백엔드에만 있나요?"**
원칙적으로는 그렇다. 다만 "장바구니에 3개 이상 담으면 버튼 색이 바뀐다" 같은 화면에만 영향을 주는 규칙은 프론트엔드에 있어도 된다. 기준은 간단하다. 손님이 조작했을 때 손해가 나면 백엔드에 두어야 한다.

### 한 줄 정리

요청은 정해진 양식의 주문서, 응답은 앞자리 숫자로 성패를 말하는 답변, 그리고 그 사이의 판단 전부가 비즈니스 로직이다. 남이 대신 짜줄 수 없는 유일한 코드가 그 판단이다.
